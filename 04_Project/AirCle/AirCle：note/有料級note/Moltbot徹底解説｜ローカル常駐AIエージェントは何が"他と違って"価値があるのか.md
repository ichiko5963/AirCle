## 第1章：Moltbot（現 OpenClaw）の概要

## 1.1 何者か？—「チャットで指示すると、実際の作業まで行う」ローカル常駐AI

**Moltbot**は、現在は**OpenClaw**という名称に移行し、公式サイト・GitHubもOpenClaw名義で運用されています。

一言で表すと：

> **「チャットで指示すると、あなたの代わりに“実際の作業”まで行う」タイプのローカル常駐AIアシスタント（AIエージェント）**

です。

- **SaaS型アシスタント**のように「誰かのサーバー上」ではなく、**自分のPC・自宅サーバー・VPS**など自分が管理する環境で動かす
- **チャットアプリ**（WhatsApp / Telegram / Discord / Slack / Signal / iMessage など）から呼び出せる
- **MITライセンスのOSS**として公開されている

開発の中心人物は **Peter Steinberger** 氏。公式ブログでは「2か月前の週末のハックが起点」だったこと、星数やトラフィックが急増したことが説明されています。

## 1.2 名前の変遷：Clawd → Moltbot → OpenClaw

名称は短期間で次のように変遷しています。

- **Clawd（Clawdbot系）** … 2025年11月頃に誕生
- **Moltbot** … 商標上の事情（Anthropic側からの要請等）により変更
- **OpenClaw** … 現在の正式名称

海外で「Clawdbot」として話題になった記事やセットアップガイドは、**同じプロジェクトの前身・別名**と考えて問題ありません。  
本稿では原則として **「Moltbot（現 OpenClaw）」** と表記し、必要に応じて Clawdbot にも言及します。

## 第2章：主な用途とユースケース

OpenClawが評価されるのは、**「チャットで答えるだけのAI」ではなく、予定・メール・Web操作・ローカル作業・定期実行までを“ひとつの運用基盤”に束ねられる**点です。

## 2.1 生活・個人業務のアシスタント化

- スマホからテキストするだけで**「PC側のブラウザ操作を伴う作業」**まで任せられる、という文脈で語られます。
- 海外メディア（Axios）では、**フライトのチェックイン・予定変更・カレンダー操作**といった“実務タスク”に触れています。
- The Verge は、WhatsApp 等のメッセージング経由で**リマインド管理・クライアント連絡**に使われている事例を紹介しています。

海外では、例えば次のような声があります。

> メールを片付ける。会議をスケジュールする。寝ている間に企業リサーチ。リードにフォローアップ。コンテンツを書く。カレンダーを管理する。  
> 多くのAIツールは「質問に答える」。Clawdbotは**「仕事をする」**。

日本語圏の具体例としては、**「毎朝7:00に天気・予定・誕生日等をまとめてTelegramに配信する朝ブリーフィング」**のような定型レポート自動化が実装例として公開されています。

## 2.2 プロアクティブ運用（定期実行・見回り）

OpenClawには、ゲートウェイ内蔵の**Cron機構**があり、

- 「毎朝実行」
- 「20分後にリマインド」
- 「定期的に状況チェック」

などをジョブとして永続化できます。ジョブは `~/.openclaw/cron/` に保存され、**再起動後もスケジュールが失われない**設計です。

**「自動で起きて、必要ならチャットに返す」**運用が、一般的なチャットAIとの差別化要因になっています。

## 2.3 開発・情報収集・業務オペレーション

- チャットから指示して**ローカルでコマンドを動かす**、問題調査や修正を進める、といった開発用途の事例が語られます。
- The Verge は、**フォーム入力・メール送信・カレンダー管理**に加え、**PC全体への権限付与（ファイル読み書き・シェル実行等）**が可能である点を具体的に述べています。

この領域は「便利さ」と「リスク」が表裏一体で、**セキュリティ設計が実運用の分水嶺**になります（後述・別記事「Clawdbot安全設計と運用の実務ガイド」も参照）。

## 第3章：「答えない、やる」— 他ツールとの決定的な違い

## 3.1 多くのAIツールは「答える」。OpenClawは「やる」

海外の解説では、次のように言い切られています。

> Most AI tools answer questions. Clawdbot does work.  
> （多くのAIツールは質問に答える。Clawdbotは**仕事をする**。）

- **Zapier / Make** … アプリ間の「つなぎ」とトリガーでワークフローを回す。実行主体は各SaaS。
- **Dify / Gumloop** … AIアプリやフローを「作る・運用する」基盤。主にクラウド上で動かす。
- **OpenClaw** … **あなたの環境で**、AIが**PC・ブラウザ・シェル・ファイル**を直接動かす。「チャット一通＝ワークフロー起動」で、**実行まで完結**する。

つまり、**同じ「自動化 × AI」の文脈でも、スタックの階層が違う**のです。

## 3.2 「30分セットアップ」の夢と、運用の現実

海外では「**30分でセットアップ、コピペでウィザードを進めるだけ**」というガイドが人気です。

- 無料サーバー（例：AWS EC2）を立てる
- インストールスクリプトを1行実行
- ウィザードでモデル・チャネル（例：Telegram）を選択
- 最初の3つの“勝ち”：**メール要約・企業リサーチ・リマインダー**を60秒以内に試す

という流れで、「非エンジニアでもできる」とされています。

一方、日本語圏の体験談では、**「“5分でインストール”は開発者向け。一般ユーザーが安全に運用するには、DockerやAPI管理などの知識が必要」**という指摘もあります。

- **できること**が広いぶん、**どこまで権限を渡すか・どこで動かすか・誰が触れるか**の設計が、体験価値を左右する
- 導入検討では、**機能より先に「権限設計・隔離・入口制御」を要件化する**ことが、最短の成功ルートです

「すぐ試す」と「安全に長く使う」の両方を、この記事と安全設計ガイドで押さえておくことをおすすめします。

## 第4章：技術的特徴（かんたん整理）

OpenClawは、Zapier/Make や Dify/Gumloop とは**アーキテクチャの思想**が異なります。キーワードは **Local-first / Gateway / Skills / Tools / Memory** です。

## 4.1 Gateway中心の“制御プレーン”

- **単一の長寿命Gateway**が、各メッセージング面（WhatsApp は Baileys、Telegram は grammY 等）を管理
- macOSアプリ・CLI・Web UI などのクライアントは **WebSocket** で接続（デフォルト `127.0.0.1:18789`）
- 「チャットアプリは入口」「実行と状態管理はGatewayに集約」という運用モデル

```text
（あなた）WhatsApp / Telegram / Slack などで指示
        ↓
   Gateway（自分のPC/VPS上）
   - セッション/ルーティング/認証
   - メモリ管理（ローカル）
   - ツール実行（sandbox/host）
        ↓
  LLMプロバイダ（OpenAI/Anthropic/Gemini/ローカル等）
        ↓
  必要に応じて実行
  - ブラウザ操作 / シェル実行 / ファイル操作 / 外部API
        ↓
（結果）チャットに返信 / 定期レポート配信
```

## 4.2 永続メモリは“ファイルが正”

- メモリのソース・オブ・トゥルースは**ワークスペース内のMarkdownファイル**
- 「ディスクに書かれたものだけを“覚えている”」という前提が明言されている
- 既定では `memory/YYYY-MM-DD.md`（日次）と `MEMORY.md`（長期）を使い分け
- メモリ検索は**ベクトル検索＋BM25**のハイブリッドで、“意味”と“完全一致トークン”の両取り

## 4.3 ツール実行とサンドボックス

- **Execツール**などでワークスペース上でシェルコマンドを実行可能。実行先（sandbox / gateway / node）、承認フロー、allowlist などのパラメータあり
- **Dockerコンテナ内に隔離するSandboxing**により、事故時の被害範囲（blast radius）を小さくする設計が取れる（完全な境界ではないが、リスク低減として明記）
- ブラウザ操作は、**OpenClawが管理する専用プロファイル**を使用。個人用プロファイルに触れない“隔離レーン”として説明されている

## 4.4 対応モデル・チャネル

- **LLM**：Anthropic / OpenAI / Gemini / xAI のほか、OpenRouter、Ollama / LM Studio などローカル実行も対応
- **チャット**：WhatsApp / Telegram / Discord / Slack / Signal / iMessage / Teams / WebChat 等
- 音声・カメラなどは**ノード**（macOS / iOS / Android 等）としてGatewayに接続する構造

## 5.2 どう使い分けるべきか

**OpenClawが刺さる条件**

- チャット導線で、**人間の代わりに“端末上の作業”まで動かしたい**（ブラウザ操作、ローカルスクリプト等）
- **データや運用を自分側に寄せたい**（Local-first、鍵の自己管理）
- **定期ジョブで“勝手に報告してくる”仕組み**が欲しい

**他ツールが向くケース**

- **社内の業務自動化を安全に横展開**するなら、Zapier/Make のような実績あるワークフロー基盤（監査・権限・テンプレ共有の成熟度）
- **AIアプリを“作って配布する/組織で運用する”**なら Dify
- **AIフローを素早く組む**なら Gumloop

## 第6章：価格体系とコストパフォーマンス

## 6.1 OpenClawの料金観

- **OpenClaw本体**はOSS（MIT）のため、**ソフト利用料はゼロ**
- 実務上かかるコスト：
  - **稼働環境**：常時稼働なら PC 電気代 or VPS 費用（例：AWS Lightsail 等）
  - **LLM利用料**：クラウドLLMを使う場合、プロバイダ課金（BYOK）
  - **周辺API**：検索API（例：Brave Search）など、機能次第で追加
  - **セキュリティ対策**：サンドボックス・アクセス制御の構成（＝運用コスト）

海外の事例では「**Claude 契約 $20/月 ＋ 無料AWSサーバ**。人間のVAは $500–2000/月で8時間睡眠。Clawdbotは24/7で $20**」といった比較もされています。  
日本語圏では、API利用料は**利用頻度で大きく振れる**（軽い利用で月 $10–30、重いと $100 超の可能性）という示唆もあります。モデル・使い方で変動するため、あくまで目安です。

## 6.2 主要ツール価格プラン（目安）

| ツール | 無料プラン | 有料の入口価格（目安） | 課金軸の典型 |
| --- | --- | --- | --- |
| Moltbot（現 OpenClaw） | OSS（ソフト代0） | 実質：VPS＋LLM利用料 | インフラ費＋LLM従量（BYOK） |
| Zapier | Free：月100タスク | Professional：年払い $19.99/mo〜 | タスク（実行数） |
| Make | Free：月1,000 credits | Core：$9/mo（10k credits/mo） | credits（モジュール実行） |
| Dify | Sandbox：無料（例：200メッセージ等） | Professional：$59/ワークスペース/月 | メッセージ/ストレージ/機能枠 |
| Gumloop | Free：2k credits/月 | Solo：$37/月（10k+ credits） | credits＋同時実行等 |

**コストパフォーマンスの結論**  
「定型のアプリ間連携を大量に回す」ほど Zapier/Make の課金設計が読みやすくなります。  
OpenClawは**“端末操作や個別最適”まで含めた価値が出る場面**で強く、そこに投資する形になります。

- 日本語の体験談では、**「一般ユーザーが安全に運用するには Docker や API 管理の知識が必要」**という指摘がある

**“できること”が広いぶん、導入・運用の難易度が体験価値を左右する**点は押さえておくとよいです。

## 第8章：セキュリティとプライバシー（要約）

OpenClawの価値は「**実行できる**」ことですが、同時に「**実行できてしまう**」ことが最大のリスクになります。

## 8.1 代表的なリスク

- **シェル・ブラウザ・メール・カレンダー**などに触れ得ること、**管理パネルの公開・誤設定**が問題化し得る（Axios 等）
- **端末への管理者レベル権限とアプリ資格情報の組み合わせ**、**プロンプトインジェクションが未解決**である点（The Verge 等）
- **人気に便乗した攻撃**：Moltbotを装ったVS Code拡張がトロイの木馬を含んでいた事案（TechRadar）、偽サイト・非公式リポジトリへの誘導（Malwarebytes）など

## 8.2 公式が推奨する対策の方向性

- **「完璧に安全な構成はない。アクセス範囲と権限を意図的に設計せよ」**という立場
- **openclaw security audit** の定期実行、DM/グループのポリシー、ブラウザ制御露出・ファイル権限・プラグインなどの“事故ポイント”を潰すことが推奨
- **ツール実行をコンテナに隔離する Sandboxing** で被害範囲を抑制
- **プライバシー**：Local-first の利点はあるが、クラウドLLMを使う限りプロンプトや一部データはプロバイダに送られる。機密性が強い場合はローカルモデル・サンドボックス強化・アクセス制御の最小化が重要

**詳細な安全設計・運用チェックリスト**は、別記事 **「Clawdbot安全設計と運用の実務ガイド｜『怖いから触らない』を『使える』に変える」** を参照してください。

## 第9章：今後の展望と総括

## 9.1 公式のロードマップ（2026年1月時点）

公式ブログ（2026-01-29）では、**Security を最優先**にしつつ、Gateway の信頼性向上、モデル/プロバイダ対応の拡張、磨き込みを進めると述べられています。  
リブランドに合わせて新チャネル追加や Web チャットのマルチモーダル対応（画像送信）、セキュリティハードニングの実施も公表されています。

## 9.2 総括：何が“他と違って”価値があるのか

**Moltbot（現 OpenClaw）**は、

- Zapier/Make のような「**アプリ統合の自動化SaaS**」とも、
- Dify/Gumloop のような「**AIフロー構築基盤**」とも、

異なります。

**「自分の環境でAIを常駐させ、チャット導線で“実行”まで完結させる」**点に独自性があります。

その価値は大きい一方で、**権限・鍵・ネットワーク露出の設計を誤ると、利便性がそのままリスクに転化**します。  
導入検討では、**機能よりも先に「どこまで任せるか（権限設計）」「どこで動かすか（隔離）」「誰が触れるか（入口制御）」を要件化する**ことが、最短の成功ルートです。

海外の言い回しを借りれば、「**多くのAIツールは質問に答える。OpenClawは仕事をする。**」  
その“仕事”を、安全に・持続可能に使うための一歩として、この記事と安全設計ガイドを役立ててもらえれば幸いです。
